# CrossMux Calendar Face — концепция и план разработки

Свой экран ожидания «Календарь» для **M5Stack Paper Mono** вместо китайского
календаря (老黄历), в виде **overlay + хуки** поверх любого состояния upstream.

| | |
|---|---|
| Upstream | `https://github.com/0x1abin/crossmux`, ветка `main` |
| Проверено на коммите | `c92edca422bc2a3087e22c2d47956e562ae1006e` (2026-09-20, версия 1.6.0) |
| Цель сборки | `pio run -e papermono` |
| Хост разработки | Arch Linux |
| Макет | `design/calendar-interactive-mockup.html` (открыть в браузере; концепт — в прошивке экраны немного отличаются, см. §12.12) |

> Все ссылки `файл:строка` ниже — по коммиту `c92edca`. При обновлении upstream
> они могут сместиться; ищите по имени символа, а не по номеру строки.

---

## 1. Что делаем

**Задача.** Заменить грань стендбая «китайский календарь» на обычный григорианский
календарь: крупное время, день недели, дата в двух форматах, сетка месяца,
номер недели и день года, погода с восходом/закатом. Работает в портрете и
в ландшафте.

**Главное ограничение.** Не форкать upstream целиком. Свой репозиторий не содержит
кода CrossMux вообще: только новые файлы (overlay), скрипт точечных правок (hooks)
и сборочные скрипты. Обновление upstream = пересоздать чистый клон и применить
overlay заново. Конфликтов git не бывает by design; вместо них — громкая ошибка
`ANCHOR LOST`, если upstream изменил форму якоря.

**Чего не делаем.** Не удаляем `ChineseCalendarFace.*` и `ChineseAlmanac.*` из
исходников upstream — только не регистрируем их в таблице граней. Меньше правок =
меньше поверхность для дрейфа.

## 2. Железо и его следствия

M5Stack Paper Mono (SKU C153), отдельная ESP32-S3 цель в CrossMux:

- ESP32-S3R8, 16 MB flash, **8 MB PSRAM** (в отличие от C3-целей X3/X4 — там ~380 KB RAM и никакого PSRAM)
- Экран 3.97″, **480×800**, SSD1677, 4 градации серого, встроенная подсветка
- Тач FT6336G (активная зона сужена: X 5–475, Y 5–795)
- RTC **RX8130CE** — часы переживают потерю питания
- IMU BMI270, microSD, кнопки A/B + Power, Wi-Fi/BLE

Следствия для нашей грани:

1. **Часы идут без сети.** Wi-Fi нужен только для погоды, не для времени.
2. **Память не узкое место на этой плате**, но грань живёт в общем дереве исходников
   с C3-целями. Правила upstream (см. §6) соблюдаем в любом случае.
3. **Grayscale есть** — можно использовать 4 уровня для выходных и дней соседних месяцев.
4. **Автоповорот по IMU** — потенциально возможен, но сначала надо проверить, отдаёт ли
   HAL данные BMI270 для papermono. В v1 ориентацию берём из настройки CrossMux.

## 3. Дизайн

Макет: `design/calendar-interactive-mockup.html` — переключатель портрет/ландшафт, инверсия, тап-зоны и вложенные экраны
(первый, «стендбай»-макет заменён им и удалён; реальные экраны — `docs/*.png`).

**Состав экрана (сверху вниз, портрет):**

| Блок | Содержимое |
|---|---|
| Статус-строка | «синхр. HH:MM · UTC+N» слева, батарея справа |
| Время | `HH:MM`, очень крупно |
| День недели | «Воскресенье» |
| Дата | `20 сентября 2026` **и** плашка `20.09.2026` — одновременно |
| Чипсы | «Нед. 38» · «День 263 / 365» |
| Погода | иконка, температура, описание, «ощущ.»; ↓ ↑ (мин/макс), ветер, осадки; восход / закат / длина дня — **значки вместо слов** (`Glyph` в `CalendarDraw`, рисуются примитивами); освободившееся место отдано сетке месяца |
| Сетка месяца | заголовок «Сентябрь 2026» со стрелками ‹ ›, 7 колонок Пн–Вс, 5 строк |

**Ландшафт:** две колонки. Слева (≈330 px) всё, кроме сетки; справа — сетка месяца.
В ландшафте у блока погоды **нет нижней разделительной линии**, а подпись «день»
у длины дня скрыта, чтобы строка не переносилась.

**Оттенки серого:**
- чёрный — время и сегодняшний день (инверсная плашка);
- тёмно-серый — выходные;
- светло-серый — дни соседних месяцев;
- если grayscale недоступен — различаем жирностью и рамкой, не цветом.

**Колонка номеров недель в сетке — убрана намеренно.** Номер недели живёт только
в чипсах под временем.

### 4.1. Интерфейс грани — `StandbyFace.h`

```cpp
class StandbyFace {
 public:
  enum class TickResult : uint8_t { None, Redraw, RedrawWithGhostCleanup };

  virtual void onEnter() {}                 // выделить состояние
  virtual void onExit()  {}                 // освободить всё, что выделено в onEnter
  virtual void onShake(uint32_t seed) {}    // «встряска» (боковые Up/Down)
  virtual void onPagePrev() {}              // ← Up
  virtual void onPageNext() {}              // ← Down
  virtual TickResult tick() = 0;            // вызывается каждый loop(); решает, нужна ли перерисовка
  virtual void render(GfxRenderer&, const Rect& viewport) = 0;
  virtual StrId titleId() const = 0;        // заголовок в шапке
  virtual uint32_t secondsUntilNextWake() const = 0;  // для light sleep
  virtual bool wantsGrayscale() const { return false; }
};
```

Важно про `wantsGrayscale()`: при включённом grayscale `render()` вызывается
**три раза подряд** (BW, LSB, MSB). Значит `render()` обязан быть идемпотентным —
никакой мутации состояния внутри. Grayscale-проход срабатывает только в режиме
Immersive и при выключенной инверсии.

### 4.2. Регистрация граней — `StandbyActivity.cpp:54`

```cpp
constexpr FaceEntry kFaces[] = {
    {[]() -> std::unique_ptr<StandbyFace> { return makeUniqueNoThrow<SloppyClockFace>(); },
     [](int, int) { return true; }},
#ifdef ENABLE_CHINESE_VERSION
    {[]() -> std::unique_ptr<StandbyFace> { return makeUniqueNoThrow<ChineseCalendarFace>(); },
     [](int sw, int sh) { return sh > sw; }},  // portrait only
#endif
};
```

Второй лямбда-параметр — предикат доступности `isAvailable(sw, sh)`. Через него
грань скрывается в неподходящей ориентации. Наша грань возвращает `true` всегда.

`ENABLE_CHINESE_VERSION=1` задан в профиле `[base]` (`platformio.ini:69`), то есть
китайская грань собирается и в `papermono`. Это и есть то, что мы убираем.

### 4.3. Ввод — что достаётся грани, а что нет

`StandbyActivity::loop()` (`StandbyActivity.cpp:428…`) разбирает ввод **до** грани:

| Жест / кнопка | Кто обрабатывает | Действие |
|---|---|---|
| свайп ←/→ (`:434`) | активность | переключение граней |
| кнопки Left/Right (`:494`) | активность | переключение граней |
| свайп ↑/↓ | грань | `onPageNext()` / `onPagePrev()` |
| кнопки Up/Down (`:474`) | грань | `onPagePrev()` / `onPageNext()` |
| тап по экрану (`:459`) | активность | переключение инверсии; **координаты грани не передаются** |
| Confirm (`:520`) | активность | инверсия |
| Back | активность | выход на Home |

**Следствия для дизайна:**
- Листать месяц можно только через Up/Down (кнопки A/B или свайп ↑/↓).
- Стрелки `‹ ›` в макете — **декоративные**: тапа по ним сейчас не будет.
  Либо убрать их, либо оставить как подсказку для кнопок.
- Возврат к текущему месяцу делаем по таймеру бездействия, а не тапом по заголовку.
- Тап по блоку погоды и по календарю (концепция — §12) потребует перехвата ввода до активности. Метод `onTap`
  в `StandbyFace` при этом **не нужен**: хватает статической функции грани и одного хука в начале `loop()`.

### 4.4. Время

`src/util/TimeUtils.h` — всё, что нужно, уже есть:

```cpp
bool     TimeUtils::isClockValid();
uint32_t TimeUtils::getCurrentValidTimestamp();          // 0, если часам нельзя верить
bool     TimeUtils::getLocalDateTime(uint32_t, std::tm&); // с учётом clockUtcOffsetQ
unsigned TimeUtils::getDaysInMonth(int year, unsigned month);
uint32_t TimeUtils::getDayOrdinalForDate(int, unsigned, unsigned);
bool     TimeUtils::getDateFromDayOrdinal(uint32_t, int&, unsigned&, unsigned&);
```

CrossMux **не вызывает** `setenv("TZ")`: местное время = системное UTC + фиксированное
смещение `SETTINGS.clockUtcOffsetQ` (в четвертях часа). Не менять TZ глобально —
это сломает остальные экраны.

Так же устроена навигация по дням в `ChineseCalendarFace.cpp:281…301` — хороший
образец для нашей логики «сегодня + смещение».

### 4.5. Wi-Fi в стендбае

`StandbyActivity::startTimeSync()` выходит сразу:

```cpp
if (TimeUtils::isClockValid() || !SETTINGS.clockAutoSync) return;
```

То есть **при живых часах Wi-Fi не включается вообще**, а после синхронизации
`stopTimeSyncWifi()` делает `esp_wifi_deinit()`. У Paper Mono есть RTC, значит
часы почти всегда валидны → для погоды нужен **свой цикл выхода в сеть**
(раз в 30–60 мин).

**Реализовано без хука в `loop()`**: цикл — конечный автомат `WeatherClient`, который крутится из
`CalendarFace::tick()` (активность вызывает его каждый `loop()`). Он не мешает синхронизации времени:
Wi-Fi поднимается, только если он свободен (`WiFi.getMode() == WIFI_MODE_NULL`); если кто-то уже
подключён — используем и не выключаем. Сеть — самая сильная из запомненных среди видимых в скане (§13.7, §13.8),
а не только последняя, как в `trySilentWifiConnect()`. HTTP — свой клиент `CalendarHttp` поверх того же wolfSSL
(`freeink::SecureClient`) с разбором по этапам и короткими таймаутами (§13.9); запасные пути к погоде — там же.

### 4.6. Шрифты и крупные цифры

`src/fontIds.h` объявляет NotoSans/NotoSerif 12/14/16/18 pt, UI 10/12, SMALL — **но это обман для
этой (унифицированной) сборки.** В `src/main.cpp:395-404` все `NOTOSANS_*` и `NOTOSERIF_*` регистрируются
на **один** `offlineReaderFontFamily` = `notosans_cjk_12`: ASCII + CJK, **без кириллицы, без жирного,
без разных размеров** (размеры даёт только загрузка шрифтов с SD). Кириллица в них рисуется как «ничто»
(глиф не найден → тихий пропуск), цифры при этом видны — поэтому ошибка легко пропускается.
Проверено в симуляторе (§8, этап 3).

Рабочие международные шрифты: **`UI_12_FONT_ID`** (Ubuntu Medium + Bold), **`UI_10_FONT_ID`**
(то же, мельче), `SMALL_FONT_ID` (notosans_8). **Больше 12 pt текста нет.**

Значит:
1. Любой текст, где есть не-ASCII (русский, немецкий), — только `UI_10/UI_12` (жирный — `EpdFontFamily::BOLD`).
2. Крупное время и температура — **свой сгенерированный шрифт** `CalendarFonts.h` (Ubuntu Medium — та же
   гарнитура, что у `UI_*`; знаки `0-9 : - °`; три размера; `tools/gen_digit_fonts.sh`, ~12 КБ в образе).
   Регистрируется в рендерере из `CalendarFace::render()` через `insertFont` (повторный вызов игнорируется).
   (Первая версия использовала `SloppyDigits` — векторные «рукописные» цифры; заменены по просьбе владельца
   на стандартное начертание.) Крупных букв нет — день недели и месяц набираются `UI_12` bold.

### 4.7. i18n

- Источник: `lib/I18n/translations/*.yaml` (34 языка), английский — эталон.
- `scripts/gen_i18n.py` запускается как **pre-скрипт сборки** (`platformio.ini:89,235`),
  генерирует `I18nKeys.h` / `I18nStrings.{h,cpp}`; они в `.gitignore` — руками не трогать.
- **Отсутствующие ключи подставляются из английского** («missing in `<lang>`, using
  English fallback»). Значит добавить ключ можно в 1–3 языка, остальные 31 не сломаются.
- Все строки UI — только через `tr(STR_…)`, хардкод запрещён правилами проекта.

### 4.8. Сборка

- `build_src_filter = +<*>` в `[base]` (`platformio.ini:75`) — **новые .cpp в `src/`
  подхватываются автоматически**, `platformio.ini` править не нужно.
  (Симулятор на `:200` переопределяет фильтр, но тоже начинается с `+<*>`.)
- Окружения Paper Mono: `[papermono_hardware]` (`:705`), `[env:papermono]` (`:724`,
  dev-сборка с serial-логом), `papermono-gh_release`, `papermono_nightly`.
- Флаг платы: `-DFREEINK_DEVICE_PAPERMONO=1` (`:715`).

### 5.1. Что делает `apply_hooks.py`

Девять хуков в 8 файлах (1–4 — грань Календаря, 5–9 — Wi-Fi Enterprise, §13.5), все идемпотентные, все ищут якоря по смыслу (хуки 3 и 4 описаны ниже):

**Хук 1 — `src/activities/apps/standby/StandbyActivity.cpp`:**

```diff
 #include "SloppyClockFace.h"
+#include "CalendarFace.h"  // [calmod]

 constexpr FaceEntry kFaces[] = {
+    {[]() -> std::unique_ptr<StandbyFace> { return makeUniqueNoThrow<CalendarFace>(); },
+     [](int, int) { return true; }},  // [calmod] обе ориентации, первая грань
     {[]() -> std::unique_ptr<StandbyFace> { return makeUniqueNoThrow<SloppyClockFace>(); },
      [](int, int) { return true; }},
-#ifdef ENABLE_CHINESE_VERSION
-    {[]() -> std::unique_ptr<StandbyFace> { return makeUniqueNoThrow<ChineseCalendarFace>(); },
-     [](int sw, int sh) { return sh > sw; }},  // portrait only
-#endif
 };
```

**Хук 2 — `lib/I18n/translations/{english,russian,german}.yaml`:** дописать
`STR_FACE_CALENDAR` в конец файла. Остальные языки возьмут английский по fallback.

**Хук 3 — `StandbyActivity.cpp`, ориентация.** Upstream применяет `SETTINGS.orientation`
(плитка в шторке / «Настройки») **только в читалке** (`ReaderUtils::applyOrientation`), а `ReaderActivity`
при выходе сбрасывает рендерер в Portrait. Стендбай ориентации не читает — поэтому без хука он всегда
портретный, хотя плитка в шторке переключается (она меняет только настройку: `FrontlightPanelActivity.cpp:172`).
Хук: `calendar_orientation::sync(renderer)` в начале `onEnter()` (после `Activity::onEnter()`, до выбора
грани по размерам) и в начале `loop()` (ловит смену из шторки), `restore()` (Portrait) перед
`Activity::onExit()`. Код — `overlay/.../CalendarOrientation.h`, +5 строк в файле.

**Хук 4 — `StandbyActivity.cpp`, перехват ввода** (§12.10): сразу после хука ориентации в начале `loop()`
`if (CalendarFace::handleInput(mappedInput, mode_ == DisplayMode::Immersive)) { …; return; }` — иначе вложенные
экраны нельзя открыть тапом, закрыть Back'ом и листать свайпом (активность забирает эти события первой).

Итог на `c92edca`: хуки 1–4 — 4 файла, +16 / −4 строки; вместе с Wi-Fi Enterprise (§13.5) — **8 файлов, +51 / −11 строк**.

```bash
./scripts/sync.sh --latest     # берёт свежий origin/main — проверка на дрейф
```

Алгоритм `sync.sh`: снести `work/`, **поверхностно** (одна ревизия, без истории — ~170 МБ вместо 275) получить нужный SHA
вместе с сабмодулями (`freeink-sdk`), скопировать `overlay/`, запустить `hooks/apply_hooks.py work/`. Если сервер не отдаёт SHA
поверхностно — откат на полный клон.

Дальше `./scripts/build.sh`. Сборка зелёная на свежем `main` → записать новый SHA
в `upstream.lock` и закоммитить. Красная → лог покажет, какой якорь потерялся.

Ночной GitHub Actions на `--latest` ловит дрейф раньше, чем вы о него споткнётесь
(этап 7).

## 6. Правила upstream, которые обязательны для нашего кода

Из `AGENTS.md` (полные формулировки — там же и в `docs/engineering/`):

1. **Базовая планка — ESP32-C3: ~380 KB RAM, без PSRAM.** Общий код должен в неё
   влезать, даже если наша плата богаче. Обосновывать каждое выделение в куче,
   предпочитать стек/статику, `.reserve()` перед циклами `push_back`.
2. **Никогда голый `new`.** Сборка с `-fno-exceptions`: неудачный `new` вызывает
   `abort()`, а не возвращает `nullptr`. Использовать `makeUniqueNoThrow<T>()`
   из `lib/Memory/Memory.h`, всегда проверять на null и писать `LOG_ERR` при OOM.
3. **Весь пользовательский текст — через `tr()`.** Логи можно хардкодить.
4. **Только HAL-классы**, не SDK напрямую (`Storage`, `HalDisplay`, `HalGPIO`).
5. **Никаких `file.close()`** для локальных `FsFile` — деструктор закрывает сам.
6. **`memcpy` для невыровненного чтения** (RISC-V падает на `reinterpret_cast`).
7. **Логические кнопки `MappedInputManager::Button::*`**, не сырые `HalGPIO::BTN_*`.
8. **Никогда не хардкодить 800/480** — только `renderer.getScreenWidth()/getScreenHeight()`.
9. **Что выделено в `onEnter()` — освободить в `onExit()`.**
10. **Не править генерируемые файлы** (`*.generated.h`, `I18nKeys.h`, `I18nStrings.*`).
11. **Соседние интерактивные элементы — минимум 6 px видимого зазора**, геометрия
    отрисовки и хит-теста берётся из одного источника.

Перед коммитом: `./bin/clang-format-fix` (нужен clang-format 21+), затем `./bin/ci-check`.

### 12.3 Тап-зоны главного экрана

| Зона | Что это | Действие |
|---|---|---|
| Блок погоды | рамка от верхней до нижней линии блока (город, температура, детали, солнце) | → «Погода», страница 1 |

Геометрия зон и геометрия отрисовки должны браться **из одного источника** (правило CrossMux №11, §6):
одна функция `computeLayout(viewport, состояние)` возвращает прямоугольники, ею пользуются и `render()`, и разбор тапа.
Для проверки попадания есть готовый `MappedInputManager::wasTapInRect(x, y, w, h)`; координаты приходят
**логическими, с учётом ориентации**, поэтому в ландшафте ничего не пересчитывается.
Минимальный размер цели — около 44 px; зазор между соседними — не меньше 6 px (у ячеек сетки он есть).

|---|---|

| Старше 3 ч | плашка «устарело · ЧЧ:ММ» вместо «обн.» |
| Старше 12 ч или нет | те же заглушки, что на главном экране: облако с косой чертой, «Нет данных», прочерки |
| Кэш старого формата (есть «сейчас», нет прогноза) | сводка есть, вместо графика/таблицы — «Прогноз загрузится при следующем подключении к Wi-Fi» |
| Нет Wi-Fi | экран открывается по кэшу; ничего не блокируется |

### 12.5 Экран «День»

Открывается по тапу на числе, для любой даты 1970–2100 (границы `CalendarCore`). Всё, кроме погоды, считается **на устройстве, без сети**.

- **Заголовок:** «Воскресенье, 20 сентября 2026» и метка «сегодня / завтра / через N дн. / N дн. назад»; строка «Нед. 38 · День 263 / 365 · осталось 102 дн.».
- **Солнце** (по месту из кэша): восход, закат, длина дня, разница со вчерашним днём («−5 мин») и мини-график длины дня за год с точкой на выбранной дате.
- **Луна:** значок фазы, название, освещённость %, ближайшие полнолуние и новолуние.
- **Погода дня** — только если дата в окне «сегодня … +6 дней»: диапазон температур, описание, осадки, ветер. Тап по карточке — на «7 дней». Иначе строка «Прогноз доступен на 7 дней вперёд».
- **Праздник** (по желанию, §12.11): «★ День Победы».
- Внизу две кнопки: предыдущий и следующий день; в шапке «Сегодня».

Про луну: в прототипе средняя фаза (ошибка до суток). Для устройства планируется расчёт истинных фаз по Meeus, «Astronomical Algorithms», гл. 49
(точность — минуты), с проверкой по опубликованным таблицам фаз; чистый модуль без Arduino, как `SunTimes`.

Про праздники: можно показывать только **фиксированные даты** (1–8 января, 23 февраля, 8 марта, 1 мая, 9 мая, 12 июня, 4 ноября).
Переносы выходных объявляет правительство каждый год отдельным постановлением, их нельзя вычислить — поэтому подписываем «праздник», а не «выходной».
Таблица лежит отдельным файлом (`Holidays.h`) и включается в `CalendarConfig.h`.

### 12.6 Экран «Год»

12 мини-месяцев (3×4 в портрете, 4×3 в ландшафте), сегодня — плашкой, текущий месяц — с инверсным заголовком.
Тап по месяцу — на главный экран, показывающий этот месяц (значение `monthOffset_`); тап «Сегодня» — на текущий год.

### 12.7 Управление внутри экранов

| Ввод | Главный | Погода | День | Год |
|---|---|---|---|---|
| Свайп ←/→, Left/Right | смена грани (как сейчас) | страница 1 ⇄ 2 | −1 / +1 день | −1 / +1 год |
| Свайп ↑/↓, Up/Down | месяц ∓1 (как сейчас) | — | ∓1 неделя | ∓1 год |
| Тап | по зонам §12.3, иначе инверсия | ✕ — закрыть | ✕, «Сегодня», ‹ ›, карточка погоды | ✕, месяц, «Сегодня» |
| Confirm | инверсия (как сейчас) | обновить погоду сейчас *(идея)* | «Сегодня» | текущий год |
| Back | выход на главную CrossMux | закрыть → главный | закрыть → главный | закрыть → главный |
| Нет ввода | Immersive через 5 с | автозакрытие через **60 с** (`kDetailAutoCloseSec`) | то же | то же |

Пока открыт вложенный экран, **смена граней свайпом отключена** — это освобождает горизонтальный свайп для страниц.
Чтобы сменить грань, нужно сначала закрыть экран.

### 12.8 Режимы экрана и обновление

- **Immersive.** Тап *по зоне* открывает вложенный экран сразу, минуя «первый ввод только будит». Так тап по погоде осмыслен и на «спящем» экране.
  Тап *мимо зон* ведёт себя по-старому. (Альтернатива — сначала будить; см. §12.11.)
- **Обновление панели.** Открытие и закрытие — полная перерисовка быстрым режимом, как при листании месяца; при закрытии просим `RedrawWithGhostCleanup`.
  Серых оттенков рендерер не даёт, поэтому всё рисуется растром и контуром, как и главный экран.
- **Сеть под открытым экраном.** Запрос погоды блокирует цикл на несколько секунд и «съел» бы свайп. Пока вложенный экран открыт,
  плановое обновление откладывается до закрытия или до 10 с без ввода.

### 12.9 Данные и сеть

Все нужные данные дают **тот же один запрос** к Open-Meteo, что и сейчас, с добавленными параметрами:

```
&hourly=temperature_2m,weather_code,precipitation_probability,wind_speed_10m,is_day&forecast_hours=24
&daily=weather_code,temperature_2m_max,temperature_2m_min,precipitation_sum,precipitation_probability_max,wind_speed_10m_max&forecast_days=7
&timeformat=unixtime
```

- **Размер ответа: 2 028 байт** (текущая погода + 24 часа + 7 дней; замерено для Москвы) — против ≈ 1 КБ сейчас. Второй запрос и второе TLS-соединение не нужны, цикл и расход батареи те же.
- **ОЗУ:** 24 × ~8 Б + 7 × ~14 Б ≈ 300 Б в объекте грани; JSON разбирается с фильтром, кучу под ответ берём как сейчас (лимит тела 4 КБ остаётся).
- **Кэш:** формат `v:2` добавляет массивы `hr` и `dy`. Кэш `v:1` читается как раньше — без прогноза (состояние «кэш старого формата», §12.4).
- Часы приходят Unix-временем, часовой пояс — из ответа (`timezone=auto`); дни недели и даты считает `CalendarCore`.
- Тестовый ответ уже лежит в `tests/data/openmeteo_moscow_7d.json`; разбор проверяем на нём и на мусорных ответах, как остальное.

### 12.10 Что меняется в коде

| Что | Как |

### 12.11 Риски и открытые вопросы

**Риски (проверить при реализации):**
- Жесты у краёв экрана обрабатывает `ActivityManager` **раньше активности**: свайп от нижнего края = «Домой» (выйдет из Standby даже с открытым экраном),
  от верхнего — шторка яркости (это нормально, после неё вернёмся), от левого края вправо — жест «Назад» (по описанию в `MappedInputManager.h`; как он доходит до Standby, не проверено — в худшем случае закроет экран, что тоже нормально).
  Листать страницы лучше начинать не у самого края.
- Наш симулятор (`env:simulator`) — класса X4, наличие тача в нём не подтверждено (при выборе языка тап по списку не сработал). Нужно проверить `TAP`/`SWIPE`; иначе тесты жестов пойдут в окружении с тачем (`simulator_x4_pro`, `simulator_sticky` упомянуты в документации симулятора) или через кнопки.
- Блокирующий HTTP во время свайпа — учтено отсрочкой (§12.8), но её нужно проверить на плате.
- Расчёт луны по Meeus: точность заявлена, а не измерена — проверить по таблицам.

### 13.1 Найдено и исправлено

### 13.2 Измерения

- **Память грани:** объект `CalendarFace` ≈ 3,3 КБ в куче (`Cache` 688 Б, `Store` календаря 1 604 Б, `HitMap` ≈ 780 Б) + `Job` ≈ 1,5 КБ и стек задачи 10 КБ **только на время выхода в сеть**; статика ≈ 630 Б (`bss`).
- **Флеш:** весь наш код ≈ 102 КБ (основное — шаблоны ArduinoJson и данные шрифта). Образ 5 993 530 Б при релизном пороге 6 029 312 Б — **запас ≈ 35 КБ**; резервов для новых крупных функций почти нет.
- **Часть производительности не измерялась на плате:** в симуляторе нет реальных таймингов ESP32-S3.

### 13.3 Сознательно оставлено

- **`std::string`/`String` при чтении и записи кэшей на SD** (два копирования на 3–6 КБ): выполняется при входе на экран и раз в 5 минут, экономия несоизмерима с риском переписывать ввод-вывод.
- **Потеря тапа во время работы процессора над кадром** (не сети): вне нашего контроля, upstream устроен так же.
- **Двойная точность в расчёте солнца и луны:** нужна для заявленной точности (≤ 2 мин и ≤ 35 с); при кэшировании стоимость незаметна.
- **Стек сетевой задачи 10 КБ** выбран по аналогии с upstream (8–16 КБ для TLS + JSON); на плате не мерился — при падениях первым делом проверить его (`kTaskStackBytes` в `WeatherClient.cpp`).

### 13.5 Wi-Fi Enterprise: логин + пароль (хуки 5–9)

**Задача.** На работе Wi-Fi просит логин и пароль прямо при подключении (WPA2-Enterprise, PEAP/MSCHAPv2); CrossMux умеет только пароль
(в его исходниках слов `enterprise`/`EAP` нет вовсе). Arduino-ESP32 умеет: `WiFi.begin(ssid, WPA2_AUTH_PEAP, identity, username, password)`.

**Как сделано — без переделки хранилища upstream.**
- Логин и пароль хранятся **одной строкой** в поле `password` штатного `WifiCredentialStore`: `"\x1F" + логин + "\x1F" + пароль`.
  Символ 0x1F с клавиатуры не набрать, поэтому спутать с обычным паролем нельзя; на SD строка обфусцируется как обычные пароли;
  «забыть сеть», отметка «сохранено», автоподключение по сохранённой сети, автосинхронизация времени, AirPage, PixelSwitch
  работают без правок. Плюс: не нужно менять формат `wifi.json`, веб-интерфейс, список сохранённых сетей.
- `overlay/src/CalmodWifi.{h,cpp}`: `compose`/`split` (чистая логика, host-тест `tests/test_wifi.cpp`), `begin(ssid, stored)` — вместо `WiFi.begin(ssid, пароль)`:
  Enterprise-строка → PEAP/TTLS, обычная → как раньше (и `esp_wifi_sta_enterprise_disable()`, если до этого был Enterprise), `timeoutMs` (ожидание ×3 для Enterprise).
- **Хуки** (`hooks/apply_hooks.py`):
  5. `WifiSelectionActivity.cpp`: запоминание Enterprise-сетей из скана (`encryptionType`), **замена `promptPasswordEntry()` целиком** (сначала логин, потом пароль;
     заменяется точный текст функции — при любом изменении upstream громкий `ANCHOR LOST`), переход ко второму шагу в `loop()`, `WiFi.begin` → `calmod_wifi::begin`, таймаут подключения;
  6–8. `StandbyActivity.cpp`, `PixelSwitchActivity.cpp`, `AirPageConnection.cpp`: `WiFi.begin(ssid, пароль)` → `calmod_wifi::begin` (собственный `WeatherClient` — напрямую);
  9. `CredentialIntegrity.h`: лимит `MAX_PASSWORD_BYTES` 64 → 160 (логин + пароль вместе), нужен только хранилищу Wi-Fi.
  Плюс строка перевода `STR_ENTER_WIFI_USERNAME` (в русском — латиницей «Wi-Fi login»: заголовок клавиатуры рисуется шрифтом без кириллицы (§4.6), иначе от «Введите логин Wi-Fi» остался бы «Wi-Fi», неотличимый от запроса пароля).
- **Настройки** (`CalendarConfig.h`): `kWifiEapMethod` (PEAP/TTLS), `kWifiEapAnonymousIdentity`, `kWifiEapTimeoutFactor`.

**Проверено.** Хуки на чистом клоне `c92edca`: применение (8 файлов), повтор (`unchanged`), потеря якоря (`ANCHOR LOST`); сборка симулятора и прошивки;
в симуляторе (`CALMOD_SIM_ENTERPRISE=1` объявляет тестовую сеть Enterprise): тап по сети → запрос логина → запрос пароля → подключение с разобранными `user`/`pass` →
«Сохранить?» → запись в `wifi.json` (обфусцирована, длина `логин+пароль+2`) → повторное чтение и подключение календарём с теми же данными.
Хост-тест упаковки: круговой проход, обычные пароли не принимаются за Enterprise, разделитель внутри пароля.

**НЕ проверено:** подключение к настоящей корпоративной точке доступа (нет её под рукой) — рукопожатие PEAP на плате, время подключения, поведение при неправильном пароле
(сервер может вернуть отказ, а плата — ждать таймаут ×3 ≈ 45 с), совместимость с конкретной сетью работодателя (метод EAP, анонимная идентичность).

**Цена и ограничения.**
- **Флеш +95 КБ** (5 996 346 → 6 091 902 Б; раздел `app0` 6 553 600 Б, занято 93 %): линкуются `wpa_supplicant` EAP/TLS. RAM практически не меняется (+1 КБ).
- **Сертификат сервера не проверяется** (CA не задан): возможен «двойник» сети. Чтобы проверять — нужен файл CA на SD и вызов `esp_eap_client_set_ca_cert` (в бэклоге).
- **Скрытые сети** не распознаются как Enterprise (нет записи в скане): нужен явный выбор типа сети (в бэклоге).
- В списке сетей Enterprise-сеть не помечена особо (звёздочка «защищена», как у любой).
- Поверхность дрейфа upstream выросла: хуков 9 в 8 файлах вместо 4 в 1–2; самый хрупкий — замена `promptPasswordEntry()`.
- Если понадобится вернуться к прежним размерам, достаточно убрать хуки 5–9 (Enterprise-строки из `wifi.json` тогда станут «паролем» со служебным символом — сеть не подключится, но ничего не сломается).

### 13.6 Остаточное изображение при смене экрана и на заставке (2026-09-22)

**Жалоба.** (1) При переходе с вложенных экранов («Погода», «День», «Год») обратно на главный остаётся остаточное
изображение. (2) При выключении устройства с открытым календарём на обложке книги / заставке виден след цифр.

**Причина — общая для обеих жалоб.** `StandbyActivity::processFaceTick()` конвертирует наш `TickResult::RedrawWithGhostCleanup`
в `renderer.requestNextRefresh(HalDisplay::HALF_REFRESH)` **только если `gpio.isXteinkDevice()`** — Paper Mono под это
не подпадает (это отдельное семейство плат, не Xteink), поэтому запрос молча отбрасывается: плановая чистка
(`kGhostCleanupEveryUpdates`, раз в 30 обновлений) и чистка на полночь никогда не долетали до экрана. Хуже того,
переходы по тапу (открыть/закрыть «Погоду», «День», «Год») вообще не проходят через `tick()` — они меняют экран прямо
в `onInput()` и зовут `requestUpdate()`, так что там `RedrawWithGhostCleanup` не запрашивался вовсе, даже на Xteink.
В сумме: время и сегодняшняя плашка стоят на экране закрашенными чёрным по многу минут подряд, upstream всю дорогу
рисует такую грань только `FAST_REFRESH` (сам он это признаёт: «Standby stays on FAST_REFRESH end-to-end… We accept
some long-term ghosting», `StandbyActivity.cpp`) — без полноценной чистки остаточный заряд копится и просвечивает
через любой следующий кадр, включая заставку при выключении (там `SleepActivity` тоже намеренно берёт `HALF_REFRESH`,
а не `FULL_REFRESH`, — см. комментарий про жалобы на мигание, issue #2471 — и такой чистки одного остаточного изображения
может не хватить, если оно успело «отпечататься» за много обновлений подряд).

**Исправлено средствами календаря — без единого нового хука.** `GfxRenderer::requestNextRefresh()` — обычный публичный
метод рендерера (не завязан на `isXteinkDevice()`), а `StandbyActivity::render()` и так вызывает `renderer.displayBuffer()`
сразу после `currentFace_->render()`. Значит грань может попросить `HALF_REFRESH` для *своего* следующего кадра прямо
из `CalendarFace::render()`, и это применится независимо от типа платы. Флаг `wantGhostCleanup_` выставляется:
- в `applyHit()` — когда тип экрана меняется (главный ⇄ вложенный, «День» → «Погода» по тапу на карточке погоды и т.п.);
- в `closeDetail()` — покрывает Back и автозакрытие по таймауту, у которых нет своего `applyHit()`;
- в `tick()` — полночь (сетка и дата целиком) и плановая раз-в-N-минут чистка (`kGhostCleanupEveryUpdates`), в
  дополнение к прежнему `RedrawWithGhostCleanup` (он остаётся, чтобы Xteink-платы получали чистку тем же путём, что и раньше).

> **Итог (исправлено в §13.8):** `HALF_REFRESH` на Paper Mono оказался бесполезен — драйвер выполняет его как обычное
> быстрое обновление. Теперь грань просит `FULL_REFRESH`, как кнопка «Обновление экрана» в верхнем меню.

`render()` в начале проверяет флаг и, если он взведён, вызывает `r.requestNextRefresh(HalDisplay::HALF_REFRESH)` —
тот же режим, которым сама `StandbyActivity` лечит `RedrawWithGhostCleanup` на Xteink, и которым `SleepActivity` красит
заставку. Простое (не тап-driven) обновление минуты или свайп месяца в этот флаг не попадают — они остаются на
`FAST_REFRESH`, листание и тиканье времени не стали медленнее.

**Проверено.** В симуляторе (`LOG_DBG` виден при `LOG_LEVEL=2`): переход главный → «Погода» → Back → «День» → Back —
каждый переход печатает ровно один `Calendar: HALF_REFRESH requested (ghost cleanup)`; простое свайп-листание месяца
и тик минуты — ничего не печатают (остаются быстрыми). Полный набор сценариев `shots.sh` и сборка прошивки — зелёные.
Флеш вырос на 140 Б (одно `bool`-поле и несколько сравнений), RAM не изменился.

**Не проверено:** физическое исчезновение остаточного изображения на реальной панели SSD1677 — в симуляторе режим
обновления не эмулируется (кадр всегда просто перерисовывается заново), сама природа ghosting'а не воспроизводима без
железа. Логика лишь гарантирует, что *запрос* на `HALF_REFRESH` теперь доходит до `displayBuffer()` в нужный момент.

**Не устранено полностью.** Если выключить устройство сразу после долгой паузы без переходов экрана (до 30 минут без
единого тапа/смены дня), плановая чистка ещё не успела сработать — след на заставке всё ещё возможен, просто реже и
слабее, чем раньше. Уменьшить окно — `kGhostCleanupEveryUpdates` в `CalendarConfig.h` (сейчас 30 обновлений ≈ 30 минут).
Более радикальное решение (просить `FULL_REFRESH` прямо перед сном) потребовало бы хука в `SleepActivity.cpp` или
`ActivityManager.cpp` — на это осознанно не пошли, следуя просьбе чинить средствами календаря, а не новыми хуками.

### 13.7 Дома Wi-Fi не подключается сам (2026-09-22)

**Жалоба.** После работы дома Wi-Fi не подключается автоматически — нужно лезть в настройки руками.

**Причина.** `WeatherClient::startJob()` брал ровно одну сеть — `WIFI_STORE.getLastConnectedSsid()` — и передавал
её `Job::run()` для слепого `WiFi.begin()`. На работе последней использованной становится рабочая сеть; дома она не
видна, `WiFi.begin()` на неё гарантированно проваливается по таймауту (`kWifiConnectTimeoutSec`, 15 с), а поскольку
подключиться не вышло, `lastConnectedSsid` так и остаётся рабочей сетью — календарь заново пробует её же на
следующем цикле, и так до тех пор, пока кто-то не подключится вручную (что заодно перезаписывает `lastConnectedSsid`
на домашнюю сеть — до следующего похода на работу). Ровно та же логика и с тем же ограничением — в самом upstream
(`StandbyActivity::trySilentWifiConnect()`, тихая синхронизация времени), но её трогать не пришлось: Paper Mono
держит время по RTC и без сети (§4.5), это не то же самое «нужен интернет».

**Исправлено полностью в `WeatherClient` (наш файл, ни одного нового хука).**
- `startJob()` теперь читает **все** сохранённые сети (до 8, `WifiCredentialStore::MAX_NETWORKS`) в `Job::candidates`,
  а не только последнюю; `lastConnectedSsid` кладётся отдельно в `Job::lastSsid`.
- `Job::run()` перед подключением делает короткий `WiFi.scanNetworks()` (обычно 1–3 с — быстрее, чем ждать полный
  таймаут на невидимой сети) и выбирает **самую сильную по RSSI сеть среди тех, что и видны в скане, и сохранены** —
  дома это будет домашняя сеть, на работе — рабочая, автоматически, без какого-либо понятия «где я сейчас».
- Если скан не нашёл ни одной сохранённой сети (либо сам не удался), последний шанс — слепая попытка `lastSsid`, как
  раньше: так по-прежнему подключаются **скрытые** сети (они не показываются в обычном скане, `WifiSelectionActivity`
  на них закрывает глаза той же оговоркой).
- После успешного подключения `applyJob()` обновляет `WIFI_STORE.setLastConnectedSsid()`, если сеть отличается от
  прежней (SD-запись — из главной задачи под тем же `RenderLock`, что и остальные присваивания результата). Это
  попутно чинит и штатную тихую синхронизацию времени: она читает то же самое поле, значит после первого же
  успешного авто-переподключения дома она тоже перестанет биться в рабочую сеть.

**Проверено в симуляторе.** Две сохранённые сети, `lastConnectedSsid` — заведомо невидимая («CorpNet»); скан (у
симулятора он фиксированный) видит только вторую сохранённую сеть — календарь подключается именно к ней, погода и
праздники загружаются, `wifi.json` после этого показывает обновлённый `lastConnectedSsid`. Отдельно проверено: ни
одной видимой сохранённой сети нет — код не падает, пробует `lastSsid` вслепую (в реальности это ветка для скрытых
сетей; симулятор не умеет по-настоящему отказывать в подключении по имени сети, поэтому фактический провал слепой
попытки на реальной несуществующей сети проверить в нём нельзя). Полный набор сценариев `shots.sh` и сборка
прошивки — зелёные. Флеш +~930 Б, RAM не изменился (кандидаты живут в уже существующем куче-объекте `Job`).

**Не проверено:** поведение на реальных двух Wi-Fi-точках (дом/работа) на плате — только в симуляторе с его
фиксированным списком «увиденных» сетей.

### 13.8 Погода не обновляется, Wi-Fi плохо переключается, неверный город по IP, остаточное изображение (2026-09-26)

**Жалобы.** Погода не обновляется; переключение между сетями (дом ⇄ работа) работает плохо; в офисе IP-геолокация
«отправила» в другой город другой страны; затирание экрана работает плохо. Пожелания: ручной выбор места с
переключателем «авто / вручную», журнал на SD для диагностики, очистка экрана как кнопкой «Обновление экрана».

(`Screen::Place`) открывается тапом по городу в шапке «Погоды». Поиск — Open-Meteo Geocoding (реальные ответы ≈ 1,5–2 КБ,

отдаёт только активности-родителю, а грань — не активность; стендбай при этом лежит на стеке и не пересоздаётся).
Заголовок клавиатуры — латиницей («City»): шрифт шапки без кириллицы (§4.6).

**Журнал** (`CalendarLog`): строки копятся в памяти (до 96 КБ, потокобезопасно — пишет и сетевая задача), на карту — раз в
`kSdLogFlushSec` и при выходе, только из главной задачи под `RenderLock` (при выходе из активности — без повторного захвата).
Сообщения прошивки копируются из её RTC-кольца последних 16 строк (`getLastLogs()`; признак новых — `logHead`), якорь —
последняя строка прошлого снимка (уникальна: «[мс]»). Причины обрыва Wi-Fi — подпиской `Network.onEvent`.

**Проверено.** Хост-тесты: поиск города на настоящих ответах, координаты, настройки, новые поля кэша, копирование журнала.
Симулятор (`CROSSPOINT_SIM_WIFI_NETWORKS`): последняя сеть «CorpNet» не видна — подключение к «HomeNet», `lastConnectedSsid`
обновлён; геолокация при смене сети; переключение «вручную» → погода заново для ручного города; поиск «москва» с экранной
клавиатуры → 4 варианта → выбор; поиск без сети → «Поиск не удался»; выход — журнал дописан; все прежние сценарии.
Прошивка собирается: флеш 6 119 894 Б (93,4 % раздела, +27 КБ), RAM без изменений.

**Не проверено (нужна плата):** реальное подключение дома/на работе (симулятор не моделирует скан, PEAP и события Wi-Fi),
фактический расход стека сетевой задачи, вид полной очистки на панели. Для этого и журнал: `/calendar-logs/`.

### 13.9 Погода не загружается ни дома, ни через телефон (2026-09-26)

**Жалоба.** «Включил календарь — погода не показывалась; пробовал две сети, домашнюю и с телефона, ни одна не работала»
(журнал `calendar-logs/2026-09-26.log`).

**Что показал журнал.** Wi-Fi исправен: скан находит домашнюю сеть, подключение за 1,9 с, адрес получен; через точку
доступа телефона — тоже. Запрос места по IP (ipwhois.app, за Cloudflare) отвечает за 0,4–2 с. А запрос погоды к
`api.open-meteo.com` **висит** (31,7 с и 37,0 с до обрыва, третий так и не закончился), 0 байт; строка ошибки прошивки
в журнал не попала (см. ниже). Стек задачи и память в порядке (свободно ≈ 10 КБ стека, ≈ 110 КБ кучи).

**Проверено на компьютере.** Тот же wolfSSL 5.7.2, собранный с настройками платы (TLS 1.3, X25519, max_fragment 2 КБ,
SP-RSA/ECC, без проверки сертификата), тем же запросом получает прогноз за 0,2 с, всего ≈ 7 КБ по сети; RSA-сертификат
и chunked-ответ Open-Meteo разбираются. Значит, дело не в коде и не в TLS, а в пути до сервера: `api.open-meteo.com` —
один адрес у **Hetzner** (AS24940, Германия), а соединения из российских сетей к этому хостингу с 2025 года
известны зависаниями. ipwhois за Cloudflare проходит. Поиск города (`geocoding-api.open-meteo.com`) — у netcup (тоже
Германия).

**Сделано.**

| Что | Как |
|---|---|
| Свой HTTP-клиент `CalendarHttp` | Этапы по отдельности: DNS → TCP (отдельным соединением даже для HTTPS) → TLS (тот же `freeink::SecureClient`) → ответ → тело. Каждый этап — `kHttpStageTimeoutSec` (10 с) вместо 60 с штатного клиента; прерывание, если грань закрыли. В журнале — строка: где остановилось, IP сервера, время этапов, объём. `Connection: close`, `Accept-Encoding: gzip` (распаковка — uzlib из прошивки, заголовок gzip и CRC — свои, `HttpCore`), свой User-Agent (`kHttpUserAgent`: MET Norway и Nominatim требуют название и контакт) |
| Запасные пути к погоде (`weather_core::Route`) | Open-Meteo HTTPS → Open-Meteo HTTP (если мешают именно шифрованию; координаты до 0,01°) → **MET Norway** (`api.met.no`, AS224 — норвежская академическая сеть). Сработавший путь запоминается в кэше и пробуется первым; запасной — не дольше `kWeatherPrimaryRetryHours` (12 ч), потом снова Open-Meteo. Цепочка считается одним запросом для «двух неудач подряд» и не обрывается бюджетом времени |
| Разбор MET Norway (`parseMetNo`) | «complete» (≈ 65 КБ JSON, по сети ≈ 5 КБ gzip): шаг 1 ч на ≈ 2,5 суток, дальше 6 ч. «Сейчас» — последний шаг не позже текущего момента; 24 часа — часовые шаги; дни — по местному времени часов устройства (MET отдаёт UTC): мин/макс из мгновенных значений и 6-часовых мин/макс, осадки — сумма часовых, где они есть, иначе 6-часовых (не перекрываются), погода дня — самый «суровый» код WMO. Значки MET → WMO (`metSymbolToWmo`; мокрый снег — коды WMO 68/69, 83/84 — добавлены в таблицу). День/ночь — по восходу/закату (`SunTimes`). «Ощущается» — из ответа, иначе по Стедману. Вероятности осадков для России нет — в почасовой таблице и на графике вместо неё миллиметры за час (`FcHour::mm`), в «7 днях» — одна строка «мм». Не чаще раза в 30 мин (`kMetNoMinRefreshMin`) — просьба сервиса. Источник подписан внизу экрана «Погода» (CC BY 4.0) |
| Поиск города | Open-Meteo Geocoding → OpenStreetMap **Nominatim** (Fastly; только населённые пункты, `featureType=settlement`; одинаковые строки «Москва-регион / Москва-город» сливаются в одну с координатами города) → Open-Meteo по HTTP. Nominatim пробуется и когда Open-Meteo ничего не нашёл |
| Журнал терял и повторял строки прошивки | Строка длиннее 255 байт (URL прогноза ≈ 450) лежит в ячейке кольца обрезанной, без перевода строки, и склеивалась со следующей — поиск «новых строк» по тексту из-за этого путал старое с новым (ложные «часть сообщений могла пропасть», повторы). Теперь копирование по ячейкам кольца (`cal_log::collect`, host-тест), по `logHead` и содержимому последней прочитанной ячейки. Строки календаря больше не пишутся через `LOG_DBG` (он кладёт их в то же 16-строчное кольцо и вытеснял сообщения прошивки) — в USB-лог идут напрямую |
| `calendar-logs/` в `.gitignore` | Журнал с устройства (имена сетей, IP) случайно не попадёт в репозиторий |

**Проверено.** Host-тесты: HTTP (URL, заголовки, chunked, длина, обрыв, до закрытия), gzip на настоящем сжатом ответе MET
(порча, потолок размера), разбор MET Norway на настоящем ответе (24 ч подряд, 7 дней по местным суткам, день/ночь,
мин ≤ макс), значки → WMO, Nominatim, кэш (источник, путь, осадки по часам), журнал по ячейкам (обрезанные строки,
повторы, оборот кольца). Симулятор: сценарий `fallback` — Open-Meteo «недоступен» по HTTPS и HTTP → погода от MET
Norway (мок — настоящий gzip-ответ), путь запомнен; экраны «Погода» и «7 дней» с подписью «MET Norway»; прежние
сценарии (`moscow`, `live`, `offline`, `stale`, `hang`). Прошивка: 6 136 622 Б (93,6 % раздела, +17 КБ), RAM без изменений.

**Не проверено (нужна плата в вашей сети):** какой из путей сработает у вас и где именно висит Open-Meteo — это покажет
новая строка журнала (`ОШИБКА TCP …` — сервер недоступен, `ОШИБКА TLS …` — мешают шифрованию, `… не ответил` — ответ
не доходит). На компьютере (сеть в Германии) проверены все три пути и wolfSSL с настройками платы.

### 13.10 «На 683dcb1 погода с Open-Meteo работала» и след на обложке (2026-09-26)

**Вопрос владельца.** На коммите `683dcb1` Wi-Fi и погода с Open-Meteo работали, плохо было только другое место и то,
что Wi-Fi не подключался сам; потом погода «сломалась».

**Сравнение кода.** Запрос погоды в `683dcb1` и позже — один и тот же: `https://api.open-meteo.com/v1/forecast…`
через штатный `HttpDownloader` (до `57931d0`), тем же wolfSSL. Меняли выбор Wi-Fi-сети (§13.7–13.8), но не адрес и не
клиент запроса.

**Что показал новый журнал (прошивка `57931d0`, дом).** Wi-Fi: подключение за 1,9–2,0 с. `ipwhois.app` — 0,4 с.
`geocoding-api.open-meteo.com` (сервер Open-Meteo у netcup) — **0,4 с**. А `api.open-meteo.com` → DNS отдаёт
`94.130.142.35` → **нет даже TCP-соединения, ни на 443, ни на 80** (по 10 с ожидания). MET Norway — 0,5 с, погода
пришла. То есть недоступен один конкретный сервер Open-Meteo из домашней сети, а не Wi-Fi и не код.

**Почему «раньше работало».** В `683dcb1` календарь подключался только к *последней использованной* сети, поэтому дома
он Wi-Fi не поднимал вовсе (владелец это и отмечал), а погода обновлялась там, где эта сеть была, — на работе; из
рабочей сети сервер доступен. Дома запрос к `94.130.142.35` впервые пошёл после автовыбора сети (§13.7) — и упёрся в
недоступный сервер. (Полностью исключить, что сервер стал недоступен именно в эти дни, по журналам нельзя.)

**Серверы Open-Meteo.** DNS `api.open-meteo.com` — геобалансировка Cloudflare: для российских подсетей —
`94.130.142.35` (Hetzner, Фалькенштайн), для других регионов — `188.40.99.226` (Hetzner) и `167.114.211.86`
(OVH, Монреаль). Все отвечают на обычный HTTP по IP с `Host: api.open-meteo.com`; HTTPS без имени сервера (SNI) не
принимают, а клиент прошивки не умеет соединяться с заданным IP под другим именем.

**Сделано.**
- Новый путь `Route::OpenMeteoAlt`: другие серверы Open-Meteo по IP из `kOpenMeteoAltServers`, обычным HTTP,
  заголовок `Host` (`cal_http::Request::hostHeader`); ответивший сервер пробуется первым до перезагрузки. Порядок:
  Open-Meteo HTTPS → другие серверы → тот же сервер по HTTP (пропускается, если он недоступен по TCP) → MET Norway.
- Соединение (TCP и TLS) ждём `kHttpConnectTimeoutSec` = 5 с вместо 10: недоступный сервер не отвечает вовсе.
- Выход из календаря больше не стирает экран в белый с полной очисткой (§13.8): след цифр под обложкой сна она не
  убирала, только мигала. Полная очистка при смене экранов, в полночь и по таймеру — осталась.

**Не проверено:** доступны ли `167.114.211.86` и `188.40.99.226` из домашней сети владельца — покажет журнал
(`погода (Open-Meteo, сервер …)`). Если нет — погода по-прежнему придёт от MET Norway.

### 13.11 Проверка на старой прошивке и единый интервал (2026-09-26)

**Проверка.** Владелец прошил `683dcb1` (старый код запроса, штатный `HttpDownloader`) и дома получил то же: погода с
Open-Meteo не приходит. Значит, недоступность сервера `94.130.142.35` из домашней сети — свойство сети, а не кода.

**Почему прошлая сессия не выходила в сеть вовсе.** В 17:10 погода пришла от MET Norway; с ним действовал интервал
30 мин (`kMetNoMinRefreshMin`), а сработавший путь держался первым 12 ч — поэтому новые запасные серверы Open-Meteo
(§13.10) даже не пробовались.

**Сделано.** Интервал для всех источников один — `kWeatherRefreshMin` (5 мин), особый интервал MET Norway убран.
Запасной путь держится первым не дольше `kWeatherPrimaryRetryMin` (60 мин), потом цепочка снова с Open-Meteo и его
других серверов (при недоступном основном это до ≈ 15 с Wi-Fi раз в час).

### 13.12 Только DNS-имена, реже запросы (2026-09-26)

**Замечание владельца.** «У меня `https://api.open-meteo.com/v1/forecast?latitude=55.75&longitude=37.62&current=temperature_2m`
работает, и по http тоже, а твой запрос — нет». Разбор: полный запрос прошивки корректен (проверен: 200, ≈ 2 КБ).
Не работали мои подсказки для проверки: адрес вида `http://94.130.142.35/…` без заголовка `Host` сервер Open-Meteo
отвергает (404) даже когда доступен, а адрес в журнале обрезан на 255 символах (так хранит кольцо прошивки) — обрезок
сервер отвергает (400). У платы же запрос не доходит до сервера: не устанавливается TCP-соединение, содержимое запроса
к этому моменту ещё не отправлено. Если браузер работает из той же сети — вероятно, у него другой путь (VPN, «частный
DNS» браузера) и потому другой сервер или маршрут; это видно по IP, к которому он подключился.

**Сделано.**
- Зашитые IP-адреса серверов Open-Meteo (§13.10) убраны: только имена через DNS сети. Цепочка: Open-Meteo HTTPS →
  он же по HTTP → MET Norway.
- Интервал: `kWeatherRefreshMin` = 15 мин (текущая погода Open-Meteo — шаг 15 мин); от MET Norway — не чаще
  `kMetNoMinRefreshMin` = 30 мин (сервис просит не спрашивать чаще, чем устаревает ответ).

### 13.13 Время в ландшафте, «Место» с главного, сохранённые места, история погоды, «Обновить» (2026-09-26)

**Журнал.** Погода обновлялась (17:59–18:09, MET Norway за 0,4–0,5 с); в сессии 18:16–18:27 новых запросов не было из-за
интервала MET Norway 30 мин (данным было 16 мин). Это ожидаемо; для ручного обновления добавлена кнопка.

**Сделано.**
- Ландшафт, главный экран: «обн. ЧЧ:ММ» показывается всегда (раньше — только когда данные устарели).
- Тап по названию города в блоке погоды главного экрана → «Место»; «Назад» возвращает туда, откуда открыли.
- «Место»: кнопка «Координаты» (клавиатура: координаты, затем подпись); список «Сохранённые» (до 5, последнее — первым,
  то же место в пределах ≈ 5 км заменяется), тап — выбрать, «x» — убрать; каждое ручное место попадает в список
  (`weather_core::addSaved`), хранится в `calendar_settings.json` (`saved`).
- «День» для прошедших дат — история: архив Open-Meteo (`archive-api.open-meteo.com`, ERA5, данные до вчерашнего
  дня; запрос ±3 дня после паузы 1,5 с в листании), плюс своя запись: последний полученный прогноз на каждый день
  (`HistSource::Recorded`) — виден, даже если архив недоступен (он тоже у Hetzner, 5.9.98.12). До 48 дней в
  `/.crosspoint/calendar_history.json`; архив запись устройства не заменяет наоборот. Повтор после неудачи — через
  `kRetryAfterFailMin`.
- «Погода»: кнопка «Обновить» внизу (в ландшафте на странице «сегодня» — под левой колонкой), пока идёт загрузка —
  «Обновляю...»; подпись под графиком заменена шапкой почасовой таблицы значками (t°, капля, ветер), как в «7 днях».

**Российские сервисы погоды без ключа.** Не нашлось: API Яндекс Погоды и Gismeteo требуют ключ/договор (и платные для
постоянного использования), у Гидрометцентра открытого API нет. При наличии ключа можно добавить как ещё один источник.

**Проверено:** host-тесты (сохранённые места, архив на настоящем ответе, хранилище истории), симулятор (сценарий
`ui`: кнопка, значки, «Место» с сохранёнными, прошедший день из архива, ландшафт), сборка прошивки
(6 145 790 Б, 93,8 %). **Не проверено на плате:** доступен ли архив из сети владельца, ввод координат клавиатурой.
